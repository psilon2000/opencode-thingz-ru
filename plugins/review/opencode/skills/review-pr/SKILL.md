# Ревью PR / Issue

Навык для системного ревью, чтобы:
- понять, что именно меняется,
- найти баги/риск/оверинжиниринг,
- отловить «scope creep» (несвязанные правки),
- подготовить короткий полезный комментарий или formal review.

## Требования

- Для GitHub-PR/issue желательно иметь `gh` и авторизацию.
- Если `gh` недоступен — работай по локальному diff/ветке (как получится), но явно скажи про ограничения.

## Важное правило

**Не повторяй то, что пользователь уже написал в обсуждении PR.**  
Сначала смотри историю обсуждений и исключай из черновика то, что уже было сказано пользователем.

## Поток работы

### Шаг 0 — Определить: PR или issue

Вход может быть:
- URL (обычно содержит `/pull/` или `/issues/`)
- просто число

Если тип неочевиден — попробуй `gh pr view <n>` (успех → PR), иначе `gh issue view <n>`.

### Шаг 1 — Собрать контекст

Для PR:

- метаданные: title/body/author/state
- размер: additions/deletions, кол-во файлов
- список файлов (группируй: код/тесты/конфиг/доки)
- обсуждение: комментарии + ревью + inline-комменты
- отдельно проверь `gh api repos/<owner>/<repo>/pulls/<n>/comments` — там часто живут реальные inline-замечания и suggested changes
- если в обсуждении есть automated review (Copilot и аналоги) — не игнорируй его автоматически, а перепроверь по коду
- статус мерджа / CI (если доступно)

Для issue:

- title/body/labels/state
- все комментарии
- есть ли ссылки на PR/коммиты
- какие файлы/модули упоминаются

### Шаг 1.5 — Выбор режима ревью

После короткого резюме спроси пользователя, что делать:

- **Quick**: только diff + метаданные (быстро, без запуска тестов).
- **Full**: глубокий разбор (контекст файлов + тесты/линтер + архитектура).

По умолчанию предлагай Full, но уважай выбор пользователя.

### Quick path (для PR)

1) Прочитай diff (`gh pr diff <n>` или локальный `git diff …`).
2) Дай коротко:
   - **Что** делает PR (2–3 предложения),
   - **Зачем** (из описания / issue / по изменениям),
   - **Размер** (мал/сред/больш),
   - **Файлы** (группами).
3) Отметь «очевидные» проблемы из diff:
   - пропущенная обработка ошибок,
   - подозрительные условия/границы,
   - TODO/FIXME/HACK,
   - отсутствие тестов на новый код,
   - «лишние» файлы, не связанные с целью PR.
4) Перейди к черновику комментария (Шаг 5).

### Full path (для PR)

**Идея:** не тащи в основной контекст большие файлы. Делегируй чтение и проверки подагенту.

1) Создай отдельную рабочую директорию через worktree (чтобы не ломать текущий checkout).
2) Запусти подагента (например, `@general`) с задачами:
   - прочитать изменённые файлы целиком,
   - прогнать тесты/линтер (определить по проекту),
   - найти архитектурные проблемы / оверинжиниринг,
   - разметить файлы по категориям: core/support/cleanup/unrelated.
3) Получи **сжатый отчёт** (без простыней кода).
4) Покажи отчёт пользователю и спроси:
   - «сделать черновик ревью?»,
   - «копнуть конкретный пункт?»,
   - «закончить без постинга?».
5) Если в отчёте есть открытые вопросы по дизайну — задавай их по одному и фиксируй ответы (они пойдут в ревью-коммент).

### Issue flow

Для issue не нужно делать worktree и гонять тесты «вслепую».  
Цель — написать полезный комментарий: анализ, вопросы, предложение решения.

### Шаг 5 — Сформировать черновик комментария/ревью

Перед черновиком:

- Убедись, что **не дублируешь** уже написанное пользователем.
- Не поднимай повторно замечания, которые уже обсуждены и закрыты в тредах.
- Если проблем нет — короткий `LGTM`/`lgtm`.

Дальше активируй стиль: используй skill `review-writing-style`.

Черновик должен быть:
- коротким,
- с конкретными пунктами,
- без пересказа «что делает PR».

### Шаг 6 — Подтверждение и публикация

Всегда сначала покажи черновик пользователю и спроси:
- «опубликовать как Approve/Comment/Request changes?»
- «отредактировать?»
- «отменить?»

Для GitHub:
- PR: `gh pr review ...`
- issue: `gh issue comment ...`

### Шаг 7 — Мердж-стратегия (если был Approve)

Если пользователь одобрил PR, предложи стратегию:
- **rebase** — если история коммитов чистая,
- **squash** — если много «wip/fixup/address review»,
- **merge commit** — редко.

Если пользователь выбрал стратегию — используй `gh pr merge ...` (и скажи, если не получилось из-за CI/защиты веток).

### Шаг 8 — Уборка

Если делал worktree — удали его и временную ветку.
