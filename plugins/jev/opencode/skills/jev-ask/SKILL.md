# Jev: массовые типизированные решения

Jev — модель решений, а не генерации: на вопрос об элементе она отвечает вероятностью «да», выбором из вариантов или оценкой по шкале. Ответ на пачку из десятков элементов приходит за доли секунды и стоит порядка $0,04 за миллион входных токенов. Основная модель решает сложное и пишет текст; Jev разгружает её от однотипных решений.

## Когда звать Jev

Явно — по просьбе пользователя: «спроси у Jev», «спроси у джев», «прогони через Jev».

Самостоятельно — если выполнены все условия:

- одно и то же решение нужно по многим элементам (ориентир — от 20): разметить, отфильтровать, разложить по категориям, упорядочить по релевантности, отобрать похожие или дубли;
- ответ типизированный: да/нет, один из заранее известных вариантов, уровень на шкале;
- ошибка на отдельном элементе недорогая или результат дальше проверяется;
- данные разрешено отправлять (ниже).

Не звать Jev:

- для одного-нескольких решений по тексту, который уже есть в контексте, — реши сам;
- для многошаговых выводов, сравнения дат, подсчётов и арифметики, сопоставления нескольких источников;
- когда нужен текст, объяснение или код;
- когда одна ошибка дорога, а проверки дальше нет.

## Какие данные можно отправлять

Данные уходят в TypeSafe (США). Можно: тексты задач, документов, MR и комментариев, рабочих чатов, журналы, результаты запросов к непродуктивным БД.

Нельзя без отдельного явного разрешения пользователя: результаты запросов к продуктивным БД, персональные данные клиентов, секреты и учётные данные.

Скрипт сам пропускает элементы с чувствительными данными:

- `--filter strict` (по умолчанию) — номера карт, телефоны, ИНН физлица, СНИЛС, паспорт, секреты, кадровые и медицинские темы;
- `--filter secrets` — только секреты и номера карт; для журналов и выборок из непродуктивных БД;
- `--filter off` — только по явному разрешению пользователя.

## Как

Главное правило: не пропускай элементы через свой контекст. Пусть команда сама соберёт их в файл или передаст через stdin, а ты прочитаешь только сводку.

Скрипт: `~/.config/opencode/scripts/jev_ask.py` (глобальная установка) или `.opencode/scripts/jev_ask.py` (установка в проект) — возьми тот, что существует.

1. Подготовь элементы: JSONL с полями `id` и `text` (другие имена — `--id-field`, `--text-field`) или по строке на элемент с `--lines`. Обычно это `jq` по выгрузке API, `grep` по журналу, `--json` у CLI или SQL-результат в JSON.
2. Сформулируй вопрос и критерии. Вопрос и описания критериев лучше писать по-английски — так модель понимает точнее; сами элементы могут быть на любом языке. В критерии включай пограничные случаи: что считается «да», а что нет. Общий контекст для всех элементов — `--state`.
3. Для больших наборов сначала `--dry-run`: сколько уйдёт и сколько отфильтруется.
4. Запусти и прочитай сводку: счётчики по меткам, уверенные примеры, элементы у порога. Полные результаты без текстов — `--out results.jsonl`, дальше соединяй их с исходными данными по `id` командой.
5. Прежде чем опираться на порог, проверь вручную 5–10 элементов, особенно у порога. Если Jev ошибается системно — уточни критерии и повтори.

```bash
# да/нет: в каких задачах нет критериев приёмки
jq -c '.issues[] | {id: .key, text: (.fields.summary + "\n" + (.fields.description // ""))}' issues.json \
  | python3 ~/.config/opencode/scripts/jev_ask.py --type noul \
      --question "Does this task description contain explicit, checkable acceptance criteria?" \
      --criteria '{"true": "Lists concrete conditions to verify the result", "false": "Only describes the goal or steps, nothing to verify"}' \
      --out no-criteria.jsonl

# выбор варианта: разложить ошибки журнала по причинам
grep -h ERROR service.log | python3 ~/.config/opencode/scripts/jev_ask.py --lines --type choice --filter secrets \
  --question "What kind of problem does this log line report?" \
  --criteria '{"db": "database or connection", "app": "application bug", "perf": "slowness", "noise": "not a problem"}'

# шкала: насколько документ отвечает на вопрос (переранжирование)
python3 ~/.config/opencode/scripts/jev_ask.py --items pages.jsonl --type score \
  --question "How well does this page answer: how are refunds processed?" \
  --criteria '["unrelated", "mentions the topic", "partially answers", "fully answers"]'
```

## Как читать результат

- `noul`: `p` — вероятность «да»; метка `yes`, если `p` не ниже порога (`--threshold`, по умолчанию 0,5).
- `choice`: метка — вариант с наибольшей вероятностью; если она ниже порога — `uncertain`.
- `score`: `score` — средневзвешенный уровень (0 — первый в списке), метка — округлённый уровень.
- Вероятности слегка плавают между запусками (на несколько сотых); не делай выводов по разнице в 0,02.
- Пропущенные фильтром элементы перечислены в сводке; реши по ним сам или скажи пользователю.

## Что сказать пользователю

Скажи, что разметку делал Jev, сколько элементов ушло и сколько пропущено фильтром, какой порог и что проверено вручную. Вероятность Jev — оценка, а не факт: окончательные выводы подтверждай по источнику.
